    MCP is an open standard by Anthropic that defines how an AI agent communicates with external capabilities — tools, resources, and prompts.

  • →

  • →
    Resources Structured data the agent can read. Files, DB rows, APIs.
  • →

    Skills

    What is a Skill?

    1

    A folder — the minimum unit of capability

    At its core, a skill is just a folder containing a SKILL.md file. That's it. No framework, no build step, no runtime required at minimum.

    2

    SKILL.md — instructions written for the agent

    YAML frontmatter (name, description) is always loaded — just enough for the agent to know when the skill is relevant. The body loads only when the skill is needed. Minimises token usage while keeping expertise on tap.

    3

    Progressive disclosure — three levels, loaded on demand

    Frontmatter → SKILL.md body → linked files (scripts/, references/, assets/). Each level loads only when needed. Skills stay lightweight until the agent actually uses them.

    Skills

    Inside a SKILL.md

    --- name: wallet-lookup description: Look up on-chain wallet balance, transaction history, and token holdings. Use when user asks to "check a wallet", "look up an address", or "show transactions". metadata: author: chaindata version: 1.0.0 ---
    # Wallet Lookup ## Instructions ### Step 1: Identify the address Extract address from user message. Valid EVM address: starts with `0x`, 42 chars. If missing, ask the user for one. ### Step 2: Run the lookup python scripts/lookup.py --address ADDR ### Step 3: Summarise Lead with ETH balance, then notable tokens, then recent activity. ## Examples User: "Check balance on 0xd8dA...?" → run lookup, return balance + top tokens
    scripts/ ← executable code, loaded on demand
    references/ ← docs & API guides, loaded on demand
    assets/ ← templates & icons, loaded on demand
    Level 1 — always in context

    The YAML frontmatter is always loaded. Just enough for the agent to know when this skill applies — without pulling in anything else.

    Level 2 — loaded when relevant

    The SKILL.md body loads once the agent decides this skill is needed. Instructions, examples, error handling.

    Level 3 — fetched on demand

    Linked files load only if the agent navigates to them. Keeps the base context small; depth is always there when needed.

    Skills

    Capabilities, packaged for agents

    An Enact skill package extends the base Skill format with a runtime manifest and implementation code. Still no special framework required.

    SKILL.md

    Plain markdown written for the agent. Teaches it what the skill does, what inputs to pass, what to expect back.

    skill.package.yml

    Runtime manifest: name, version, scripts, build hooks, secrets, and execution backend.

    code/

    Anything from a small script to a full application. Enact builds, signs, and runs it — locally, in Docker, or remotely.

    # skill.package.yml enact: "2.0.0" name: chaindata/wallet-lookup version: "1.2.0" description: Look up on-chain wallet balance and history from: python:3.12-slim hooks: build: - pip install -r requirements.txt env: CHAIN_API_KEY: secret: true scripts: lookup: "python wallet.py {{address}}"

    The problem

    Skills exist. Trust doesn't.

    Discovery

    Skills are scattered

    GitHub repos, npm packages, random blog posts. There's no central place to find a skill for a given task.

    Trust

    Who published this?

    No verification. No signing. The code running inside your agent's tool call could be anything.

    Provenance

    What changed in v1.1?

    No audit trail. No transparency log. No way to prove a published version hasn't been tampered with.

    "You wouldn't curl | bash from a random URL.
    Why would you let your agent do it?"

    The solution

    Enact — a runtime and registry for agent skills

  • 1
    Publish Push a skill. Enact builds it, signs it with Sigstore, logs to Rekor.
  • 2
    Discover Agent calls enact_search via MCP. Finds skills by capability, not by name.
  • 3
    Govern The runtime verifies signatures, enforces trust policy, selects backend (local / Docker / remote), and injects secrets — before execution.
  • 4
    Run Isolated execution. The agent never sees secrets. The model decides what to run; Enact decides whether and how.

    Secrets & environment

    Skills declare what they need.
    Enact injects it.

    Secrets are declared in the manifest, registered once with the runtime, and injected at execution time — never exposed to the agent or printed in logs.

  • 1
    Declare in manifest Mark env vars as secret: true in skill.package.yml
  • 2
    Register once Developer sets the value via CLI or config — stored in the Enact keystore
  • 3
    Injected at runtime Skill sees a normal env variable. Agent never sees the value. Logs stay clean.
    • # 1. Declare in skill.package.yml env: FIRECRAWL_API_KEY: secret: true BASE_URL: default: "https://api.example.com" # 2. Register the secret once $ enact env set FIRECRAWL_API_KEY \ fc-your-key --secret ✓ Stored in Enact keystore # 3. Run — secret injected automatically $ enact run enact/firecrawl:scrape \ -a '{"url": "https://example.com"}' ✓ FIRECRAWL_API_KEY injected (agent never saw the value)
